The readiness units are stopped; production app/migration007/gateway/worker activation is pending. Commits and PR #55 were subsequently created; latest CI and production execution validation are in progress. See [runtime evidence](../../docs/qa/2026-11-05/external-engine-runtime.md) for evidence and limits.

The DB worker calls `extractDocument(format, bytes)`; native formats stay in `readDocument`. External bytes go to one fixed HTTPS origin, `POST /v1/extract/{hwp,doc,ppt,pdf}`, `application/octet-stream`. No file names, paths, URLs or options are accepted. TLS 1.3 requires a client certificate. Worker-only environment: `DOCUMENT_EXTRACTOR_URL`, `DOCUMENT_EXTRACTOR_CA`, `DOCUMENT_EXTRACTOR_CERT`, `DOCUMENT_EXTRACTOR_KEY` (PEM values). Do not expose these to Next public environment or parser containers. Missing configuration returns `failed` with a fixed Korean reason.

The gateway owns only `/run/secrets/{client-ca,server-cert,server-key}.pem`. It has no DB/API/mail credentials, Docker socket, production mount or database route. Only the dedicated worker can reach it. Its certificate trust store must contain only the dedicated worker client CA, not a broad corporate/public CA.

## Runtime gate

**Do not enable this gateway until `test_isolation.py` passes on the actual runtime.** No fallback exists when isolation cannot be created. Historical 2026-11-04: the shared host denied user namespace UID mappings and no host/AppArmor/seccomp settings had been changed at that time. The dedicated, scoped runtime described below was installed and passed on2026-11-05; the HTTP gateway remains inactive.

Provision a dedicated gateway UID 1000 and parser UID/GID 65534. The trusted gateway needs only CAP_SETUID and CAP_SETGID so its fixed launcher can attach the child to the delegated cgroup, clear groups and drop permanently to 65534 before unprivileged bubblewrap. Do not grant SYS_ADMIN, privileged Docker or a Docker socket. Unprivileged user/mount/PID/network namespaces must be available to UID 65534. The gateway's single threaded server prevents concurrent extraction. Do not mount gateway credentials under `/usr`, `/lib`, `/lib64`, `/opt/tika` or `/opt/parser`.

Delegate cgroup v2 at exactly `/sys/fs/cgroup/extractor` to the gateway, enable memory/cpu/pids controllers in its parent and mount only that delegation writable. Parser jobs get memory.max 384MiB, memory.swap.max 0, cpu.max 0.5 CPU, pids.max 64 and memory.oom.group 1. The parent service/container must also enforce 512MiB, 0.5 CPU, 128 pids and a readonly filesystem. Requests create separate cgroup, namespace, procfs and 128MiB tmpfs. Parent env and FDs are not inherited; gateway keys, DB addresses, host paths and other jobs are absent. Failed setup returns `sandbox_unavailable`; it is never a successful extraction.

Wall time is 60s for native external parsing, up to 120s only when PDF OCR is needed. PDF's JVM watchdog starts at process entry; launcher deadline caps the entire process tree. cgroup.kill and killpg kill detached descendants/process groups. Input 5MiB, expanded stream total 20MiB, 20 pages/slides, 200k text characters, 5k blocks, wire output 2MiB; no partial output survives parser failures. OCR uses fixed local `tesseract -l kor+eng --psm 3`, 150dpi and <=10M pixels per page. OCR always returns `limited` with an uncertainty warning.

## Dedicated systemd readiness runtime (applied and verified2026-11-05; stopped after testing)

Ubuntu 24.04's user namespace restriction remains enabled. The alternative to nested Docker is a **new, separately confined readiness unit**, rooted in the verified extractor image. It does not start the HTTP gateway or connect to an app/DB. No existing service, Docker profile or global sysctl is changed.

`runtime/ghostmanual-extractor-readiness@.service` uses systemd 255 `Delegate=cpu memory pids` and `DelegateSubgroup=gateway`. Only this unit's cgroup root is exposed at `/sys/fs/cgroup`; the supervisor is in `gateway`, and `bootstrap.py` creates/enables `extractor`. The outer memory/swap/CPU/pid controls are also separate read-only file bind mounts, with AppArmor write denial: root ownership alone is not a boundary because the trusted gateway has SETUID. A bounded forked probe changes only its own UID to0 and attempts the same existing control values through direct and proc-root alias paths; every write must be denied. Parent UID/capabilities and control values remain unchanged. Jobs remain constrained to 384MiB/64pids/0.5CPU beneath a 512MiB/128pids/0.5CPU parent. Bootstrap rejects missing delegation, writable/wrong outer limits and missing host UID/capability/NNP controls.

The trusted supervisor host bounding/ambient capabilities are **SETUID and SETGID only**. Before executing bubblewrap, its child explicitly clears effective/permitted/inheritable capability data and all ambient capabilities after changing UID/GID to65534, then enforces NNP. A non-root-to-non-root UID change alone does not clear those sets. The actual pre-unshare probe requires all four sets zero and setuid(0) denied; the final untrusted payload also requires zero capability sets. The residual bounding mask is not effective permission and cannot restore capabilities with zero inheritable/ambient sets and NNP; exported setid bits/xattrs are stripped as a second defense. The enforcing named AppArmor profile allows namespace/mount operations at bubblewrap's fixed `/tmp`/`/newroot` staging locations and fixed pivots; it has no unconfined mode, broad mount rule or change_profile rule. Its sys_admin/net_admin/setpcap/sys_chroot MAC permissions do not grant those Linux capabilities in the host user namespace; bubblewrap needs them only after creating an unprivileged user namespace. The bounding set is checked before the harmless probe. The profile is selected only for this unit; it does not auto-attach to host Python. Host sudo users remain trusted administrators, not a security boundary of this profile.

The unit has an immutable root, private devices/network/tmp, hidden other-user processes and no real credentials, host home, Docker socket or production mount. ProtectKernelTunables=no, ProtectKernelLogs=no and ProtectHostname=no are deliberate for the trusted gateway's proc view: their proc overmounts conflict with the kernel mount-too-revealing check when bubblewrap creates fresh procfs in its new user/PID namespaces. The actual per-property matrix reproduced EPERM for each of these three settings; changing only these three to no passed the combined synthetic namespace probe. ProtectProc=invisible, ProtectClock=yes, ProtectKernelModules=yes and all other unit restrictions remain. AppArmor still denies proc/sys writes and keeps same-profile ptrace restrictions; the host capability bound remains SETUID/GID only. The untrusted parser still receives fresh user/PID/proc/UTS namespaces, clears all effective/permitted/inheritable/ambient capabilities and retains NNP. Explicit read-only outer cgroup controls and the actual isolation gate remain mandatory. ProcSubset=pid is omitted because bubblewrap 0.8 reads /proc/sys/kernel/overflowuid and overflowgid during startup. No additional proc bind is required. This readiness unit has no network gateway listener.
