## 문서로 작업을 시작하는 방법

이 문서는 문서별 책임과 진행 순서를 정하는 진입점이다. 기술 결정은 해당 번호 문서, 상세 변경 설계는 `superpowers/specs/`, 구현 단계는 `superpowers/plans/`, 실행 결과는 [진행 기록](구현_진행_기록.md)에서 관리한다. 같은 내용을 여러 문서에 복제하기보다 기준 문서를 링크한다.

요청 접수 → 99에 작업 등록 → 주관 문서·연결 문서 확인 → 필요한 설계·계획 → 구현/문서 수정 → 관련 검증 → 10·진행 기록 갱신 → 99 상태·다음 행동 갱신 순서로 진행한다. 문서 존재만으로 해당 기능의 구현·검증 완료를 뜻하지 않는다.

모든 작업은 00·99에서 시작하고 10·진행 기록·99에서 마무리한다. 여러 영역이 바뀌면 주관 문서는 하나 정하되 연결 문서를 함께 갱신한다.

### Superpowers 적용

| 상황 | 적용할 절차 | 남길 근거 |
|---|---|---|
| 새 기능·제품 동작 변경 | brainstorming으로 목적·범위·인수 조건 정리 | 01·02·관련 설계와 사용자의 결정 |
| 여러 단계의 구현 | writing-plans → 승인된 방식으로 executing-plans 또는 선택한 subagent-driven-development | 관련 `superpowers/plans/`와 작업 상태 |
| 버그·예상 밖 결과 | systematic-debugging으로 재현·원인 확인 | 09의 재현과 원인, 관련 문서 |
| 기능/결함 구현 | test-driven-development로 실패 재현→최소 구현→관련 suite | 10·진행 기록의 RED/GREEN 결과 |
| 구현 마무리 | requesting-code-review와 verification-before-completion | 검토 결과·수정 근거·검증 결과 |
| 오탈자·링크·문서 구조만 정비 | 기존 결정 보존, 내용·링크·현재/이력 구분 검사 | 10의 문서 검사 결과 |

설치·도구 명령은 [개발 도구 가이드](개발_도구_가이드.md)를 따른다. 사용자가 이미 승인한 범위와 실행 방식은 다시 승인받기 위해 되돌리지 않는다. 문서 수정만으로 새 제품 기능·외부 배포를 승인받았다고 간주하지 않는다. 자동 생성 도구가 문서 내용을 알아서 갱신하는 구성은 아니며, 작업자가 이 절차에 따라 갱신한다.

### 검증 선택과 완료 기준

| 변경 범위 | 실행/확인 | 주의 |
|---|---|---|
| Markdown·문서 연결만 | 필수 파일·내부 링크·작업별 책임·이력 구분, `git diff --check` | 제품 테스트 성공으로 확대하지 않음 |
| 코드·입력·HTTP·서버 | 관련 회귀, `npm test`, `npm run typecheck`, `npm run lint` | 완료 전 실제 출력과 종료 코드 확인 |
| DB·트랜잭션 | migration, `npm run test:integration` | 명시적 전용 DB 이름이 `_test`로 끝나야 함 |
| 화면·사용자 흐름 | build·`npm run test:e2e`·실제 desktop/mobile 확인 | 합성 자료·별도 Owner/Reader 세션 |
| 배포·운영 | CI·이미지·migration·health·rollback·기존 서비스 영향 | 로컬 성공과 실제 대상 배포 성공을 분리 |
| 실 AI·프록시·보안 검사 | 실제 제공자 요청·품질/비용·검사 결과 | 계정·키·예산과 접근 필요, fixture 성공과 구분 |

한 작업의 완료 조건은 요청 범위와 인수 조건 충족, 영향 문서 갱신, 실제 검증 결과, 남은 위험·미검증 항목, 다음 행동까지 기록하는 것이다. PR 생성·병합·운영 반영은 각각 별도 상태다.

### 기록 형식

99에는 `작업 ID | 우선순위 | 주관/연결 문서 | 상태 | 선행 조건 | 다음 행동 | 완료 조건·근거`를 쓴다. 상태는 `대기/진행/차단/검증 대기/완료/보류`를 쓰고 근거 없는 백분율을 만들지 않는다.

10에는 `확인일 | 파일/영역 | 확인 범위 | 기준 commit/작업 트리 | 검사 명령 | 종료 코드·결과 | 미검증/후속`을 쓴다. 결정에는 날짜·선택·이유·영향 문서를 기록하며 이미 실행된 작업을 이력 확인 없이 재실행하지 않는다.

`99_해야할일.md`가 작업 목록의 단일 기준이다. 요청한 [99_해야할일..md](99_해야할일..md)는 호환 진입점이며 별도 목록을 관리하지 않는다.

## 2026-10-16 확인 범위

기존 12개 번호 문서가 존재함을 확인했고 본문을 검토해 작업 절차를 보완했다. 제품 구현 파일은 이미 있으며 아래 최초 설계의 “코드 없음” 표현은 2026-10-03 당시 기록이다. 실제 SQL·API 계약은 현재 구현을 우선하고 제안과 차이는 해당 문서에 표시한다.

개발 도구 변경의 기준 commit `da539582`는 [PR #1](https://github.com/P-GISE/GhostManual/pull/1)에 있고, [제품 CI](https://github.com/P-GISE/GhostManual/actions/runs/38879012823)와 [Iron Laws 변경 파일 검사](https://github.com/P-GISE/GhostManual/actions/runs/38879013183)가 성공했다. 이 근거는 해당 commit의 결과이며 이후 코드 변경에 자동 적용하지 않는다. 실제 AI와 공개 운영 상태는 이번 문서 작업에서 다시 조사하지 않았다. 이전 비공개 AWS 기록과 현재 공개 가용성을 혼동하지 않는다.

## 목적과 현재 상태
GhostManual의 요구사항, 설계, 실제 구현 증거를 구분해서 관리한다. 현재 승인된 구현 계획 실행 단계다. 제품 소스·DB·API·화면이 구현됐고 기존 CI에서 unit41·integration39·E2E20·Docker 이미지 빌드를 확인했다. AWS 비공개 앱의 실제 사용자 API 흐름과 정리 타이머 첫 실행도 확인했다. 최신 모바일 CSS 변경의 전체 페이지27개 캡처·두 독립 화면 검증과 최종 CI의 단위41·통합39·브라우저20개·Docker 이미지 빌드가 모두 통과했다. AWS 비공개 갱신·롤백도 확인했다. 문서의 초기 설계 상태와 실행 결과는 진행 기록의 날짜를 기준으로 구분한다. 공개 배포와 실제 AI 실행은 아직 검증하지 않았다.
두 사용자 프롬프트를 원문 그대로 [requirements](requirements/제품_정의_프롬프트.md)에 보존했다. 현재 기술·배포 조사는 [배포 구성 검토](배포_구성_검토.md), 상세 제안은 [MVP 설계안](superpowers/specs/2026-10-03-ghostmanual-mvp-design.md)에 있다.
프로젝트 시작점은 [루트 프로젝트 가이드](../PROJECT_GUIDE.md)다. [구현 계획](superpowers/plans/2026-10-03-ghostmanual-mvp.md)과 [진행 기록](구현_진행_기록.md)을 추가했다. 사용자의 계속 진행 요청을 상세 설계 승인과 구현 계획 작성으로 반영했다.

## 상태 표기
- 확인됨: 실제 읽은 파일, 사용자 명시 요구, 실행 출력에 근거. 사용자 요구 확인과 구현 확인은 별개다.
- 제안: 설계 선택이며 존재하는 기능이나 승인된 세부사항을 뜻하지 않는다.
- 추정: 근거가 불충분한 가설. 추정을 근거로 구현 완료를 선언하지 않는다.
- 미확인: 접근·실행·사용자 결정이 필요.
- 미구현: 현재 조사한 로컬 프로젝트에 해당 제품 코드가 없음.
- 구현 완료: 관련 테스트·실행·사용자 흐름 증거와 검증 시점이 모두 있는 경우만 사용.

## 업데이트 규칙
제품 결정은 이력의 날짜·결정·근거·영향 문서를 기록한다. 상세 설계 승인 여부와 배포 승인 여부를 따로 기록한다.
기능 변경은 02·05·99, schema 변경은 03·04·10, API 변경은 04·06·07, 화면 변경은 06·10, 배포 변경은 08·09·10을 같이 확인한다.
코드와 문서가 충돌하면 현재 실행 코드와 결과를 먼저 확인한다. 제안 경로가 실제 생성되면 ledger의 상태를 갱신한다.
검증에는 명령, 종료 코드, 날짜, 결과 요약, 관련 파일을 남긴다. 코드 변경 후 이전 검증 결과를 새 코드의 증거로 재사용하지 않는다.
secret·계정 연락처·토큰·원문 업무 개인정보는 문서나 로그에 복사하지 않는다.
