# 운영 DB 최소 권한·외부 백업 — 2026-11-02 KST

사용자가 기존 AWS 계정의 S3 전용 저장소·30일 보관을 선택했고, Google 저장소 적용 가능성도 확인하도록 요청했다. 신규 IAM 권한과 30일 영구 만료는 저장 직전 별도 승인을 받아 적용했다. 로컬 PC의 저장소·설정은 변경하지 않고 원격 서버에서 수행했다.

## 실제 적용과 검증

- 앱 이미지/소스는 dc57d30bc76b83f767f3ac5e7d54ba0c076ae9aa / sha256:07defe2ad30023f0b58d34b3038f3190f3b811c79f1020da0e0f245cdd5b4325 유지. 앱 컨테이너만 재생성했다. 배포 영수증과 다른 서비스 컨테이너는 유지했다.
- 앱 접속을 ghostmanual_app으로 전환했다. 관리자 속성·상속·역할 멤버십이 없고, public 스키마 객체 생성·변경·삭제와 migration 이력 수정이 금지된다. 앱 데이터의 SELECT/INSERT/UPDATE/DELETE와 소유자가 이후 만드는 테이블의 기본 DML 권한은 허용한다. PostgreSQL 기본 TEMP 권한은 별개다. 일회성 프로비저닝 SQL은 deploy/database-runtime-role.sql을 따른다.
- 기존 ghostmanual 소유자/관리자는 DB 관리·백업용으로 유지한다. 비밀번호는 앱 환경에서 제거하고 /etc/ghostmanual-migration.env(root:root 0600)에 관리자 접속 URL을 보관한다. 이 파일은 Docker --env-file 형식의 raw 값이며 따옴표를 붙이지 않는다. 운영 .env에 APP_DATABASE_PASSWORD를 추가하고 Compose의 app DATABASE_URL만 바꿨다. AI·Google·메일 설정과 DB 서비스는 그대로다.
- 실제 앱 pool 역할/권한 검사, HTTP 로그인·프로필 조회/수정·자료 CRUD·매뉴얼 수정/게시·공유/회수·계정 삭제 PASS. 합성 계정과 자료는 정리했고 AI 호출은 0회다. 관리자 전용 환경으로 현재 이미지의 scripts/migrate.ts를 실행해 Migrations ready(변경 없음)를 확인했다.

이번 검증에서 사용한 현재 이미지의 관리자 migration 확인 명령(변경 없음, 서버 root 셸)이다. 새 배포의 migration에는 현재 이미지 대신 새 릴리스의 검증 이미지를 사용한다([배포 절차](../deploy/README.md)).

```sh
docker run --rm --network ghostmanual_default \
  --env-file /etc/ghostmanual-migration.env \
  "$(docker inspect -f '{{.Image}}' ghostmanual-app-1)" node scripts/migrate.ts
```

## 외부 백업

- 전용 버킷: ghostmanual-backups-pgise-20261102, ap-southeast-2(시드니). 공개 접근 4종 차단, ACL 비활성, SSE-S3 AES256, 버전 관리 비활성.
- 서버 역할 PGISE-S1-SSMAgent에는 이 버킷의 postgres/*에 대한 PutObject/GetObject만 별도 정책으로 부여했다. 객체 삭제·다른 버킷·버킷 관리 권한은 추가하지 않았다. 장기 AWS 키를 발급하거나 앱에 전달하지 않는다. 앱 컨테이너의 IMDSv2 토큰 요청은 2초 내 접근 불가였다.
- 버킷 정책은 HTTP와 조건 없는 PutObject를 거부한다. 백업은 고유 키와 If-None-Match:*로 덮어쓰기를 막고 SHA-256을 검증한다.
- postgres/ 백업은 생성 30일 후 만료 대상이며 실제 삭제는 S3 비동기 처리다. 버전 관리를 나중에 켜면 보존 규칙을 다시 검토해야 한다.
- ghostmanual-backup.timer 활성화 완료. 매일 18:20 UTC = 다음 날 03:20 KST. 최초 예약은 2026-11-03 03:20 KST다. 첫 수동 서비스 실행 성공과 실제 예약 성공은 구분한다.
- 실제 첫 백업 81,405 bytes를 S3에 올리고 다시 내려받았다. AES256/원본 SHA256 일치와 네트워크·운영 볼륨이 없는 PG18의 전체 트랜잭션 복원, 필수 테이블 5개 확인 PASS. 컨테이너 삭제 실패 주입 시에도 다운로드 덤프 삭제와 비정상 종료를 확인했다.
- AWS CLI 2.39.3은 공식 PGP 서명을 검증해 /opt/ghostmanual/tools/bin/aws에 설치했다. 서비스 PATH에 이 경로를 지정했다. 구현/복구 절차는 [백업 가이드](../deploy/backup/README.md)를 따른다.

점검: `systemctl list-timers ghostmanual-backup.timer --all`, `journalctl -u ghostmanual-backup.service --since yesterday`, `systemctl --failed`. 성공 로그의 객체 키와 SHA256을 사용해 가이드의 격리 복원 시험을 수행한다. 실패 알림을 외부로 전송하는 연동은 추가하지 않았다.

백업에는 DB 안의 원본 파일·계정·매뉴얼 데이터가 들어간다. 운영 .env·클러스터 역할/비밀번호·이미지·EBS 자체는 백업 대상이 아니다. 일일 백업이므로 최장 약 하루의 변경 손실 가능성이 있고, 서버 중지·백업 실패가 이어지면 더 길어진다. 복구에는 관리자 자격 증명과 같은 버전의 PostgreSQL이 별도로 필요하다.

## Google 저장소 비교

Google Drive는 별도 Drive OAuth 동의/갱신 토큰 또는 조직 공유 드라이브 인증·30일 만료 작업이 필요하다. 현재 앱 Google 로그인(openid email profile)은 백업 권한이 아니다. Google Cloud Storage도 가능하나 GCP 프로젝트·버킷·결제와 AWS 연합 인증, 수명 주기/soft delete 설정을 추가로 운영해야 한다. 현재 AWS 호스트 역할을 재사용하는 S3를 적용했고 Google 저장소를 이중으로 생성하지 않았다. [인증·보관 비교와 공식 문서](../deploy/backup/README.md#저장-대상-비교).

## EBS 실제 상태와 확인 방법

AWS 콘솔 시드니 리전 → EC2 → Elastic Block Store → 볼륨에서 서버 인스턴스 i-0b4a251ecd2f5bd3e에 /dev/sda1로 연결된 vol-02e91bd89ed39c404(gp3 30 GiB)를 대조했다. 암호화 열은 **암호화되지 않음**이다. 앞선 EC2 API 조회 권한 거부로 미확인이던 상태를 이번 인증된 콘솔 조회로 확인했다.

기본 EBS 암호화를 켜도 이 기존 볼륨이 즉시 암호화되지는 않는다. 암호화된 스냅샷 복사/새 볼륨 준비와 계획된 루트 볼륨 교체가 필요하다. 같은 호스트의 다른 서비스도 영향을 받으므로 이번에는 중지·교체·재부팅하지 않았다. 별도 복구 검증·중단 계획과 사용자 승인 후 진행할 후속 작업이다. [AWS 볼륨 정보 확인](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-describing-volumes.html).

## 기록과 후속

원격 .omo/evidence/ops-hardening/의 DB 권한 검토, 운영 HTTP 검증, 실제 백업/복원, 서명/실패 회귀, backup-gate를 근거로 한다. 원본 .env/Compose와 신선한 pg_dump는 root 전용 rollback-runtime-role-* 폴더에 보존했다. 비밀 값·덤프 내용은 Git에 포함하지 않는다.

자동 앱 배포는 별도 인프라 채팅과 승인받아 순서를 조율했다. 이 작업의 쓰기 동안 legacy deploy timer를 중지했으며, 새 배포 설치 담당에게 최종 메타데이터와 쓰기 창을 반환한다. 이 백업 타이머와 앱 배포 타이머는 별개다. 운영 적용 결과와 이 변경을 반영하는 검토용 PR의 CI·병합 상태는 구분한다.
