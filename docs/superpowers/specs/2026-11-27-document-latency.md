# 문서함·파일 등록·읽기 지연 단축 범위

기준은 PR119 병합47168fc와 병합 후CI45951476014이다. 사용자는 프로젝트 문서 최신화와 팀 이름 변경 뒤 상단 경로 수정, 문서함/등록/읽기 대기 시간 단축 방안 준비를 요청했다. 이 문서는 **개선 준비안**이며 서비스 지연 실측 결과나 성능 개선 완료 보고가 아니다.

## 목적과 구간

사용자에게 보이는 시간을 하나의 “업로드 시간”으로 합치지 않는다.

| 흐름 | 측정 경계 |
|---|---|
| 문서함 | 클릭→세션 전환→HTML/JS→개요 응답→업무 카드 사용 가능 |
| 등록 | 클릭→브라우저 해시/유사 자료 조회→전송→정적 검사/용량 확인→원본·큐 저장→201/202 |
| 추출 | 큐 등록→claim→네이티브/격리 변환/OCR→완료 저장→클라이언트 완료 감지 |
| 읽기 | 세션/Owner·Reader 결정→자료→이력/최신 상세→JSON 수신→본문 사용 가능 |

XLSX는 요청 안에서 읽어201로 등록하고, DOCX/HWPX/PPTX 등은202 후 비동기 처리한다. 202와 추출 완료를 같은 완료 지표로 비교하지 않으며 동기 XLSX의 큐 대기는 N/A로 기록한다. 파일 다운로드와 추출 미리보기도 나눈다.

## 코드로 확인한 후보 — 시간은 미측정

- src/components/Teams.tsx와 src/lib/teams.ts: 상단 경로/등록 화면은 현재 문서함을 알기 위해 전체 소속 목록을 읽는다. 기존 경로 컴포넌트는 표시하지 않는 화면에서도 조회했다. 이번 경로 수정은 표시할 때만 조회하며, SourceForm·TeamPage 등의 독립 조회는 유지한다. 표시 대상 경로 이동에서는 정확성을 위해 재조회하므로 모든 이동이 빨라졌다고 주장하지 않는다.
- src/lib/overview.ts: RR 안의 권한 확인·전체 counts·팀별 통계·페이지 조회가 순차 진행된다. 페이지20팀/10업무와 별개로 집계 비용은 전체 허용 후보에 영향을 받는다.
- src/lib/session.ts의 lockAccountSession: 문서함 FOR UPDATE 잠금은 읽기와 쓰기의 대기를 만들 수 있다. 대기 시간 측정 없이 삭제하지 않는다.
- src/components/SourceDetail.tsx: 세션 확인 후 자료, 자료 준비 뒤 양식 목록을 읽는다. Owner/Reader 선택을 먼저 확정하는 의미가 있다.
- src/components/FileVersions.tsx: 이력 뒤 최신 상세를 읽고 처리 중에는2초 주기로 상세를 재조회한다. TemplateDetail도2초 주기다.
- src/components/DocumentChanges.tsx: 전체 추출JSON을 받은 뒤 최초100블록만 표시한다.
- src/components/SourceForm.tsx: 버전 문서는 브라우저 SHA256과 유사 자료 확인을 거쳐 전송한다.
- src/app/api/sources/route.ts, src/lib/document-sources.ts, src/lib/file-sources.ts: 수신·정적 검사·권한 재확인·용량 합산·원본/큐 저장이 접수 응답 전 경로에 있다.
- src/lib/document-jobs.ts와 scripts/document-jobs.ts: 문서 처리1개를 직렬 claim하고 문서→양식 순서로 처리한다. 모두 없으면1초 대기한다. 설정상1초·2초 주기와 실제 지연은 구분한다.
- tests/performance/measure-native-documents.ts: 기존46표본은 파서 프로세스·자원 검증이다. HTTP·DB·큐·화면의 전체 지연 측정으로 대체하지 않는다.

## 개선 순서

1. **측정/요청 수 정리**: 동일 세션의 중복 metadata 요청·전송 바이트·구간별 시간을 먼저 기록한다. 사용자별 p50/p95와 실패율·자원을 함께 비교한다.
2. **초기 화면 왕복 축소**: 현재 문서함 전용 응답, 요청 범위 중복 제거, 권한이 확정된 초기 자료/이력 응답 묶음을 검토한다. 새 API 계약과 공유 독자 분리는 검토 후 선택한다.
3. **집계 비용 축소**: 같은 RR·권한 필터 안에서 실행 계획/인덱스·중복 집계 축소를 검토한다. pg 단일 트랜잭션에 Promise.all을 붙이는 것을 병렬 최적화로 간주하지 않는다.
4. **경량 상태 조회/필요할 때 상세 읽기**: 처리 중 상태 응답에서 본문·셀·전체 추출JSON을 제외하고 완료 때 상세를 한 번 읽는 방안, 블록 페이지/펼칠 때 조회를 검토한다. 폴링 간격만 줄이지 않는다.
5. **큐·추출**: 대기와 실제 파서 시간을 분리한 뒤 공정성·문서/양식 스케줄을 검토한다. 병렬 수 확대·native/OCR 분리·알림 방식은 메모리/OOM·인증·긴 연결 비용을 측정한 뒤 별도 설계한다.
6. **브라우저/수신 복사 비용**: 해시가 UI를 막는지, multipart/Buffer 복사가 큰지 측정한 뒤 필요하면 작업 분리/복사 축소를 검토한다. 서버 해시·정적 검사·내구 저장은 생략하지 않는다. XLSX를 비동기로 바꾸는 것은 별도 계약 변경이다.

## 측정 준비

- 변경 전후 동일 commit/image·합성 자료·CPU/메모리·콜드/웜 조건을 기록한다.
- 첫 smoke는 측정 경계가 맞는지 확인한다. 비교 보고는 워밍업과 표본 수를 밝히고 대표 사례를 최소30회 반복해 p50/p95·원시 표본을 남긴다. 넓은 행렬은 별도 시간 예산을 정한다.
- 팀1/5/20개, 업무10/50/200개를 구분한다. 팀 생성5개 제한은 유지하고 큰 가입 목록은 다른 소유자의 팀에 가입한 합성 구성으로 만든다. 50초과 업무는 기존 이동 경로로 가능한 상태를 격리 fixture로 재현하며 신규 등록 제한을 완화하지 않는다.
- DOCX/HWPX/PPTX/CSV·동기 XLSX를 먼저 비교하고, 외부 변환·일반/스캔PDF·HWP/DOC/PPT는 전용 격리 환경이 준비된 뒤 구분 측정한다.
- 검증된 작은 허용 fixture와5MiB 경계·페이지/블록 많은 fixture를 나눈다. 정상 처리와 안전 거부(413/422 등)는 따로 보고한다.
- 초기 동시 사용자1명, 이후 자원 제한 안에서3명. SQL 실행 시간·pool 대기·잠금 대기와 HTTP 재시도 횟수를 별도로 기록한다. SQL별5초 timeout을 화면 전체 목표로 쓰지 않는다.
- 등록 접수·큐 등록·claim·파서 완료·저장·다음 상태 응답/paint의 구간을 연결한다. 로그에는 합성 case명·시간·바이트·상태만 두고 실제 파일명/원문/셀/토큰/이메일을 기록하지 않는다.
- 초기 HTML/JS/폰트와 LCP/INP는 API 지연과 별도로 관측한다. CI localhost 비교와 실제 사용자 네트워크/프록시·운영 지연은 구분한다. 현재 운영 속도는 이번 작업에서 측정하지 않는다.

## 반드시 유지할 경계

- 운영 배포·DB014/backfill/대표 지정·공유 운영 서버 부하 시험을 실행하지 않는다.
- 모든 Owner/Reader·세션·소속·권한 회수 재확인, 완료 시 권한 재확인을 유지한다.
- logout/문서함 전환 뒤 이전 응답 차단과 공유 독자 게시본 범위를 유지한다. 전역 권한 캐시나 RR 해제로 시간을 줄이지 않는다.
- 문서함 전환의 전체 reload는 현재의 상태 분리 경계다. CSR 전환으로 바꾸려면 별도 보안 설계·회귀 검증이 필요하다.
- 버전 문서5MiB·TXT/Markdown256KiB·용량 합산·원본/버전 보존·검사 전 게시/다운로드 차단·매크로/암호/ZIP 폭탄 거부·AI 전송 범위·기존 개인 자료/공유 링크를 유지한다.
- 새 클라우드 자원·운영 증설·큐 병렬 확대·실제 AI/메일 호출은 이번 준비안의 실행 범위가 아니다.
