# 팀 문서함 설계 (TEAM-LIBRARY 1차)

작성: 2026-11-17 · 박효민 결정 · 박기성 검토 필요(migration 009, 세션·권한 경계, 업무 옮기기)

## 1. 목적과 배경

지금은 계정 하나에 문서함 하나이고, 다른 사람은 읽기 전용 공유 링크로만 본다. 계정을 지우면 문서함도 사라진다. 인수인계 서비스인데 자료가 전임자 계정에 묶여 있다.

팀 문서함은 여러 사람이 들어가는 문서함이다. 사람이 떠나도 업무·버전 기록·매뉴얼이 팀에 남고, 새로 온 사람이 팀원으로 들어와 이어서 올린다.

## 2. 목표 / 비목표 / 반목표

목표
- 팀 문서함을 만들고 이메일로 팀원을 초대한다.
- 팀원은 팀 문서함의 모든 업무에 새 버전을 올리고, 질문에 답하고, 매뉴얼을 쓰고 게시한다.
- 팀원이 나가거나 계정을 지워도 그 사람이 올린 자료가 팀에 남는다.
- 개인 문서함의 업무를 팀 문서함으로 옮긴다.

비목표 (1차 범위 아님)
- 회사 아래 부서를 두는 계층, 게시 전 승인 절차, 읽기 전용 팀원 역할
- 팀에서 개인으로 되돌리기, 팀 사이 옮기기
- 실시간 공동 편집, 변경 알림 메일
- 사이트 관리자 페이지의 팀 목록·팀별 용량과 AI 조정
- 구독·결제, 회사 로고

반목표 (이렇게 되면 실패)
- 팀원이 아닌 사람이 팀 문서함의 자료를 보거나 고침. 내보낸 팀원이 계속 접근함
- 초대 메일을 전달받은 다른 사람이 팀에 들어옴
- 업무를 옮기다가 기록 일부가 원래 문서함에 남거나 다른 문서함에 보임
- 관리자가 한 명도 없는 팀이 생김
- 기존 개인 문서함과 공유 링크의 동작이 달라짐

## 3. 결정 사항

박효민 결정
1. 팀 관리자가 팀 문서함을 만들고 팀원을 초대한다. 사람이 떠나도 자료는 팀에 남는다.
2. 역할은 팀 관리자와 팀원 둘이다. 읽기만 하는 사람은 기존 공유 링크를 쓴다.
3. 팀원은 팀 문서함의 모든 업무를 고칠 수 있다. 업무 삭제는 올린 사람과 팀 관리자만 한다.
4. 초대는 이메일 주소로 하고 그 이메일 계정만 수락할 수 있다.
5. 개인 문서함은 유지한다. 개인 업무를 팀으로 옮길 수 있고 반대 방향은 없다. 옮기기는 작업 순서의 맨 뒤다.

작성자 기본값 (박효민 확인함)
- 상단에 문서함 전환 메뉴를 두고 마지막에 본 문서함을 기억한다.
- 한 사람이 만들 수 있는 팀은 5개, 팀당 30명.
- 초대는 7일 뒤 만료된다. 팀 관리자가 취소하고 다시 보낼 수 있다.
- 팀원은 스스로 나가거나 팀 관리자가 내보낸다. 올린 자료와 버전 기록의 이름은 남는다.
- 팀 관리자가 한 명뿐이면 나가기와 계정 삭제 전에 다른 관리자를 지정해야 한다. 혼자 남은 팀이면 팀을 삭제해야 한다.
- 팀 삭제는 팀 관리자만 하고, 팀 이름을 입력해 확인한다. 모든 자료가 영구 삭제된다.
- 동시에 고치면 나중에 저장한 사람에게 "다른 사람이 먼저 고쳤습니다. 새 내용을 확인하세요"를 보인다(기존 충돌 검사).
- 매뉴얼을 게시한 사람의 이름을 기록하고 보인다.
- 공유 링크는 팀원 누구나 만들고 끈다.
- 회사 양식은 문서함 단위다. 팀 문서함의 양식은 팀원 모두 쓰고 등록하며, 삭제는 올린 사람과 팀 관리자만 한다.
- 팀 문서함의 저장 용량은 100 MiB 고정(개인과 별도).
- AI 하루 한도는 문서함 단위 그대로다.
- 사이트 관리자가 AI를 차단한 계정은 팀 문서함에서도 AI를 쓸 수 없다. 팀 단위 차단은 없다.
- 업무를 옮겨도 기존 공유 링크는 유지된다.

작성자 판단 (설계 중 정함, 확인 필요)
- 팀 문서함은 새 종류의 `workspaces` 행이다. 업무·매뉴얼·공유는 지금처럼 `workspace_id`로 격리되므로 그 코드를 고치지 않는다.
- 권한은 매 요청마다 팀원 표를 다시 확인한다. 내보내면 다음 요청부터 접근이 끊긴다.
- 공유 링크로 들어온 후임자가 팀 매뉴얼에 질문할 때는 계정별 AI 차단을 적용하지 않는다(팀 문서함에는 주인 계정이 없다).
- 이미 가입한 사람을 초대해도 자동으로 넣지 않고 수락을 받는다.

## 4. 사용 흐름

팀 만들기와 초대
1. 문서함 전환 메뉴 → "팀 문서함 만들기" → 팀 이름 입력. 만든 사람이 팀 관리자가 된다.
2. 팀 설정 → 이메일 입력 → 초대 메일 발송. 목록에 "대기 중"으로 보인다.
3. 받은 사람이 메일의 링크를 열고 그 이메일로 로그인(없으면 가입)하면 수락 화면이 나온다. 다른 이메일로 로그인하면 초대받은 주소가 아니라고 안내하고 수락을 막는다.
4. 수락하면 팀 문서함으로 전환된다.

팀에서 일하기
- 전환 메뉴에서 문서함을 고른다. 문서함, 자료 등록, 양식 메뉴는 고른 문서함을 대상으로 한다.
- 업무 카드와 버전 기록에 올린 사람이 보인다(버전 기록에는 이미 있다).
- 업무 삭제 버튼은 올린 사람과 팀 관리자에게만 보인다.

나가기와 내보내기
- 팀 설정에서 "팀 나가기" 또는 팀 관리자의 "내보내기". 자료는 남는다.
- 나간 사람의 세션이 그 팀을 보고 있었으면 개인 문서함으로 돌아간다.

업무 옮기기
- 개인 문서함의 업무 카드 → "팀으로 옮기기" → 내가 속한 팀 선택 → 확인.
- 버전 기록, 원본 파일, 질문과 답변, 매뉴얼 초안과 게시본, 공유 링크, 후임자 질문 기록이 함께 옮겨진다.
- 팀의 저장 용량이 모자라면 옮기지 않고 이유를 알린다.

## 5. 데이터 (migration 009, 박기성 검토 필요)

```sql
ALTER TABLE workspaces ADD COLUMN team_name text
  CHECK (char_length(team_name) BETWEEN 1 AND 40);   -- 값이 있으면 팀 문서함
CREATE TABLE workspace_members(
  workspace_id uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  user_id uuid NOT NULL REFERENCES users ON DELETE CASCADE,
  role text NOT NULL CHECK(role IN ('admin','member')),
  joined_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY(workspace_id,user_id)
);
CREATE INDEX workspace_members_user ON workspace_members(user_id);
CREATE TABLE workspace_invites(
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  email text NOT NULL CHECK(email=lower(email)),
  token_hash text UNIQUE NOT NULL,
  invited_by uuid REFERENCES users ON DELETE SET NULL,
  expires_at timestamptz NOT NULL,
  accepted_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX workspace_invites_open ON workspace_invites(workspace_id,email) WHERE accepted_at IS NULL;
ALTER TABLE sources ADD COLUMN created_by uuid REFERENCES users ON DELETE SET NULL;
ALTER TABLE manual_versions ADD COLUMN published_by_name text
  CHECK (char_length(published_by_name) BETWEEN 1 AND 40);
```

- 개인 문서함은 지금처럼 `workspaces.user_id`로 주인을 안다. 팀 문서함은 `user_id`가 비어 있고 `team_name`이 있다.
- 팀 문서함은 만료로 지워지면 안 된다. `workspaces.expires_at`과 정리 작업(`src/lib/retention.ts`)이 팀 문서함을 지우지 않도록 박기성이 확인한다.
- `sources.created_by`는 삭제 권한에만 쓴다. 기존 행은 개인 문서함 주인으로 채운다. 올린 사람의 계정이 지워지면 비게 되고, 그 업무는 팀 관리자만 삭제할 수 있다.
- 사용자 삭제 시 `workspace_members`는 함께 지워지지만 팀 문서함과 자료는 남는다. 마지막 관리자 규칙은 계정 삭제 API에서 먼저 검사한다.
- 초대 토큰은 해시만 저장한다(기존 세션·공유 토큰과 같은 방식).

## 6. 세션과 권한

- 로그인 세션은 지금처럼 문서함 하나를 가리킨다(`sessions.workspace_id`). 전환은 이 값을 바꾼다.
- 세션을 해석할 때마다 다음을 확인한다: 세션의 사용자가 그 문서함의 주인(`workspaces.user_id`)이거나 `workspace_members`에 있는가. 아니면 개인 문서함으로 되돌린다.
- `SessionContext`에 `teamRole: "admin" | "member" | null`과 `userId`를 더한다. 기존 `role: "owner"`는 "편집할 수 있는 사람"의 뜻으로 유지해 업무·매뉴얼 코드를 고치지 않는다.
- 공유 링크 Reader 세션은 변함없다. 팀 API는 Reader에게 404다.
- 권한 표

| 동작 | 팀 관리자 | 팀원 | 그 밖 |
|---|---|---|---|
| 업무 등록·새 버전·답변·매뉴얼·게시·공유 링크·양식 등록 | 가능 | 가능 | 404 |
| 업무 삭제, 양식 삭제 | 가능 | 본인이 올린 것만 | 404 |
| 초대·초대 취소·내보내기·역할 변경·팀 이름 변경·팀 삭제 | 가능 | 403 | 404 |
| 팀 나가기 | 다른 관리자가 있을 때 | 가능 | 404 |

- 회사 양식의 권한 검사(`src/lib/template-extraction.ts`의 `assertTemplateOwner`와 워커의 작업 검사)는 지금 "세션 사용자가 그 문서함의 주인 계정"을 요구한다. 팀 문서함에는 주인 계정이 없으므로 팀원 검사로 함께 바꾼다. 바꾸지 않으면 팀 문서함에서 양식을 쓸 수 없다.
- AI 호출: 요청한 계정의 `ai_allowed`가 false면 차단한다. 하루 한도는 문서함 단위 그대로다.
- 저장 용량: 팀 문서함은 100 MiB 고정으로 검사한다. 개인 문서함은 지금처럼 계정 한도를 쓴다.

## 7. 업무 옮기기 (박기성 설계·구현)

- 한 트랜잭션에서 그 업무에 딸린 모든 행의 `workspace_id`를 바꾼다. 대상은 `workspace_id`를 가진 테이블 가운데 업무에 딸린 전부다(migration 001·005·007에 흩어져 있다). 목록은 박기성이 확정한다.
- 자식 테이블이 `(workspace_id, id)` 복합 외래 키로 묶여 있어 순서나 제약 처리(지연 제약 또는 ON UPDATE CASCADE)가 필요하다.
- 원본 파일의 저장 위치가 문서함에 묶여 있으면 함께 옮긴다.
- 옮긴 뒤 검사: 원래 문서함에 그 업무의 행이 0개, 팀 문서함에서 버전·매뉴얼·게시본·공유 링크가 열림.
- 진행 중인 문서 분석 작업이나 AI 작업이 있는 업무는 옮기지 않고 "분석이 끝난 뒤 다시 시도하세요"를 보인다.
- 요청한 사람이 원래 문서함의 주인이고 대상 팀의 팀원이어야 한다.

## 8. API

| 경로 | 동작 |
|---|---|
| `GET /api/workspaces` | 내 개인 문서함과 속한 팀(이름, 역할) |
| `POST /api/workspaces` | 팀 만들기 |
| `PATCH /api/workspaces/[id]` | 팀 이름 변경 |
| `DELETE /api/workspaces/[id]` | 팀 삭제(본문에 팀 이름) |
| `POST /api/session/workspace` | 문서함 전환 |
| `GET /api/workspaces/[id]/members` | 팀원과 대기 중인 초대 |
| `PATCH /api/workspaces/[id]/members/[userId]` | 역할 변경 |
| `DELETE /api/workspaces/[id]/members/[userId]` | 내보내기, 본인이면 나가기 |
| `POST /api/workspaces/[id]/invites` | 초대 메일 발송 |
| `DELETE /api/workspaces/[id]/invites/[inviteId]` | 초대 취소 |
| `POST /api/invites/accept` | 초대 수락(토큰) |
| `POST /api/sources/[id]/move` | 업무를 팀으로 옮기기 |

- 팀원 목록은 이름·소속·역할·가입일만 내보낸다. 이메일은 팀 관리자에게만 보인다.
- 초대 발송은 기존 메일 발송 한도를 따르고, 가입 여부를 응답으로 알려 주지 않는다.
- 기존 `DELETE /api/me`(계정 삭제)는 마지막 관리자 규칙에 걸리면 409와 해당 팀 이름을 돌려준다.

## 9. 화면

- 상단 전환 메뉴: 현재 문서함 이름, 내 문서함과 팀 목록, "팀 문서함 만들기".
- `/team`: 팀 이름, 팀원 목록(역할 변경·내보내기), 초대 입력과 대기 목록, 팀 나가기, 팀 삭제.
- `/invite`: 초대 수락. 로그인 전이면 로그인으로 보냈다가 돌아온다.
- 문서함: 팀 문서함일 때 업무 카드에 올린 사람 표시. 개인 문서함의 카드에 "팀으로 옮기기".
- 매뉴얼 보기: 게시한 사람 이름.
- 계정 설정: 속한 팀 목록, 계정 삭제 전 마지막 관리자 안내.
- 도움말에 팀 문서함 설명을 추가한다.

## 10. 검증

- 통합(권한이 핵심): 팀원이 아닌 계정과 Reader의 모든 팀 API·팀 자료 접근 차단, 내보낸 직후 접근 차단, 다른 이메일 계정의 초대 수락 차단, 만료·취소된 초대 차단, 마지막 관리자의 나가기·계정 삭제 차단, 팀원 계정 삭제 뒤 자료 유지, 삭제 권한(올린 사람·관리자), 저장 용량과 AI 한도의 문서함별 계산.
- 옮기기: 옮긴 뒤 원래 문서함에 남은 행 0개, 버전·매뉴얼·게시본·공유 링크·후임자 질문이 팀에서 열림, 용량 부족과 분석 중 거부, 실패 시 전부 되돌림.
- 회귀: 기존 개인 문서함·공유 링크·관리자 페이지 테스트가 그대로 통과.
- E2E: 팀 만들기 → 초대 → 다른 계정이 수락 → 그 계정이 새 버전 올림 → 원래 계정이 버전 기록에서 확인 → 내보내기 뒤 접근 불가.
- 접근성: 전환 메뉴, 팀 설정, 초대 수락.
