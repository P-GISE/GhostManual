# 랜딩 페이지·로그인 설계

변경일: 2026-10-23 (KST). 상태: 설계 초안, 사용자 승인 대기. 제품 코드·schema·배포는 아직 바꾸지 않았다.

## 1. 결정과 이유

2026-10-23 멘토링 피드백으로 사용자가 다음을 정했다.

- 서비스가 무엇인지 한눈에 보이는 **랜딩 페이지**를 만든다. 화면은 간결하게 한다.
- **로그인을 만든다.** 방식은 **이메일+비밀번호와 구글 로그인 둘 다**다.
- **로그인 필수로 바꾼다.** 지금의 "로그인 없이 7일 임시 공간" 방식은 없앤다.
- 중간평가(2026-11-06)까지 순서는 **랜딩 → 로그인 → 엑셀 비교**다.

근거: 멘토 피드백(보안 문제, 로그인 필요, 서비스가 명확히 보이는 화면). 판매·관리 기능(어드민·구독·로고)은 이번 범위가 아니다.

## 2. 목표

- 처음 방문한 사람이 랜딩 페이지에서 서비스가 무엇이고 어떻게 쓰는지 30초 안에 이해한다.
- 이메일+비밀번호로 가입·로그인·로그아웃할 수 있다.
- 구글 계정으로 가입·로그인할 수 있다.
- 로그인한 사용자는 자기 문서함 하나를 갖고, 자료가 7일 뒤 지워지지 않는다.
- 다른 사용자의 자료는 볼 수도 바꿀 수도 없다.
- 기존 기능(자료 등록·매뉴얼 작성·검수·게시·후임자 공유·질문)은 그대로 동작한다.

## 3. 비목표

- 팀 생성·초대·팀 권한, 어드민 페이지, 사용량 제한·구독 결제, 회사 로고. 후속(사업화)이다.
- 비밀번호 찾기·이메일 인증. 메일 발송 서비스가 필요하므로 후속이다(위험은 9절).
- 구글 외 소셜 로그인(카카오·네이버 등).
- JWT. 이유는 6절.
- 기존 익명 임시 공간의 자료를 계정으로 옮기기. 배포 후 7일 안에 만료된다.

## 4. 실패로 보는 경우

- 로그인 없이 다른 사람의 문서함이나 자료에 접근할 수 있다.
- 비밀번호를 평문이나 되돌릴 수 있는 형태로 저장하거나 로그에 남긴다.
- 로그인 화면이 복잡해서 심사위원·후임자가 쓰기 어렵다.
- 랜딩 페이지가 기능 설명으로 길게 늘어진다.
- 기존 매뉴얼 흐름·공유·접근성 검사가 깨진다.

## 5. 화면

### 5.1 랜딩 페이지 (`/`, 로그인 없이 볼 수 있음)

간결하게 한 화면 반 정도로 구성한다.

1. **첫 화면:** 한 문장 소개와 버튼 두 개(`시작하기` → 가입, `로그인`). 소개 문장 예: "작업을 마친 업무 파일을 올리면, 바뀐 부분의 이유를 묻고 후임자용 인수인계 매뉴얼로 남깁니다."
2. **사용 순서 3단계:** 파일 올리기 → 바뀐 부분 질문에 답하기 → 후임자에게 공유.
3. **차별점 3개:** 버전 기록, 변경 이유 질문, 검수된 매뉴얼과 근거.
4. **아래쪽:** 개인정보·이용약관 링크(기존 화면).

로그인한 사용자가 `/`에 오면 버튼 자리에 `내 문서함으로`를 보여준다. 아직 만들지 않은 기능(파일 비교)은 "준비 중"으로 표시하고 이미 되는 것처럼 쓰지 않는다.

### 5.2 가입 (`/signup`)·로그인 (`/login`)

- 이메일, 비밀번호(가입 때는 이름도 받음) 입력란과 `구글로 계속하기` 버튼.
- 오류 문구는 "이메일 또는 비밀번호가 올바르지 않습니다"처럼 어느 쪽이 틀렸는지 알려주지 않는다.
- 로그인 후 `/manuals`(내 문서함)로 이동한다.
- 상단 내비게이션에 이름과 `로그아웃`을 둔다.

### 5.3 후임자 공유 링크

공유 링크로 들어온 후임자는 **로그인 없이** 읽기 전용으로 본다. 지금처럼 링크에 만료·취소가 있다. 후임자가 계정을 만들어야 하면 인수인계가 번거로워지기 때문이다. (작성자 판단, 12절에서 확인 요청)

## 6. 로그인 방식

- **세션:** 지금 쓰는 방식(무작위 토큰을 HttpOnly 쿠키로 주고, DB에는 토큰 해시만 저장)을 그대로 쓰고, 세션에 사용자를 연결한다.
- **JWT를 쓰지 않는 이유:** JWT는 서버가 기록 없이 토큰만 검사하므로, 로그아웃·계정 삭제·탈취 시 즉시 끊기가 어렵다. 지금 구조는 DB 세션 행을 지우면 바로 끊긴다. 서버 한 대 규모라 JWT의 장점(서버 여러 대에서 DB 조회 없이 확인)도 필요 없다.
- **비밀번호:** Node 내장 `scrypt`로 사용자별 salt와 함께 해시한다. 8자 이상 128자 이하. 비교는 시간 일정 비교를 쓴다.
- **구글 로그인:** OAuth 2.0 인가 코드 방식 + PKCE + `state` 검사. 구글이 확인한 이메일(`email_verified=true`)만 받는다. 사용자 식별은 구글 계정 고유 ID(`sub`)로 한다.
- **계정 연결:** 구글 이메일이 기존 이메일 가입 계정과 같으면 같은 계정에 연결한다. 구글이 이메일을 확인했기 때문이다.
- **세션 기간:** 30일. 로그아웃하면 해당 세션 행을 지운다.
- **요청 보호:** 기존처럼 변경 요청은 `Origin` 검사, 쿠키는 `HttpOnly; SameSite=Lax; Secure(https)`. 로그인·가입은 IP 기준 시도 횟수 제한(기존 `rate_counters` 사용)을 둔다.

## 7. 데이터 (제안)

- `users`: id, email(소문자 저장, 유일), name(1~40자), password_hash(구글 전용이면 비어 있음), google_sub(유일, 비어 있을 수 있음), created_at.
- `workspaces`: `user_id`를 추가한다. 사용자당 문서함 하나. 사용자 문서함은 만료되지 않는다(`expires_at` 비움 또는 먼 미래 — 구현자 판단).
- `sessions`: 소유자 세션에 `user_id`를 추가한다. 후임자(reader) 세션은 지금처럼 공유 링크에 묶인다.
- 기존 익명 workspace 행은 그대로 두고 기존 7일 정리로 사라지게 한다.
- 파일 버전 설계의 "올린 사람·팀 직접 입력"은 **이름을 계정 이름으로 자동 기록**하고, 팀은 계정 설정에서 직접 입력하는 것으로 바꾼다. 팀 계정은 후속이다.

## 8. API (제안)

| 메서드·경로 | 동작 |
|---|---|
| POST `/api/auth/signup` | 이메일·이름·비밀번호로 가입, 문서함 생성, 로그인 쿠키 발급 |
| POST `/api/auth/login` | 이메일·비밀번호 로그인 |
| POST `/api/auth/logout` | 현재 세션 삭제 |
| GET `/api/auth/google` | 구글 로그인 시작(state·PKCE 저장 후 이동) |
| GET `/api/auth/google/callback` | 구글 응답 확인, 가입 또는 로그인 후 `/manuals`로 이동 |
| GET `/api/me` | 로그인 사용자 이름·이메일 |
| DELETE `/api/me` | 계정과 문서함 전체 삭제 |

기존 `POST /api/workspaces`(익명 공간 만들기)는 없앤다. 합성 예제는 문서함 안의 `예제 불러오기` 버튼으로 옮긴다(작성자 판단).

## 9. 보안·운영

- 구글 로그인에는 Google Cloud에서 OAuth 클라이언트를 만들어야 한다. 사용자가 직접 만들고, 값은 서버 `.env`(`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`)에만 넣는다. Git·문서·로그에 쓰지 않는다. 리디렉션 주소: `https://ghostmanual.pigs0516.com/api/auth/google/callback`, 로컬 `http://localhost:3200/api/auth/google/callback`.
- 이메일 인증이 없으므로 남의 이메일로 가입할 수 있다. 그 이메일 주인이 나중에 구글로 들어오면 같은 계정에 연결되는 문제가 있다. 대응: 이메일 가입 계정에 구글을 연결할 때는 **비밀번호로 로그인한 상태에서만** 연결하거나, 이메일 인증 도입 전까지 자동 연결을 하지 않는다(12절에서 결정 요청).
- 비밀번호 찾기가 없으므로 비밀번호를 잊으면 복구할 수 없다. 화면에 안내한다.
- 개인정보 처리방침에 계정 정보(이메일·이름)와 보관·삭제 방법을 추가한다. 자료가 7일 뒤 자동 삭제되지 않는다는 점도 바꿔 쓴다.
- 서버 저장 용량: 7일 만료가 없어지면 자료가 쌓인다. 사용자당 자료 수·크기 상한을 둔다(값은 구현자 판단).

## 10. 테스트와 인수 조건

- L1 랜딩 페이지가 로그인 없이 열리고, 데스크톱·모바일에서 가로 넘침이 없다.
- L2 이메일 가입 → 로그아웃 → 로그인 → 내 문서함 진입.
- L3 틀린 비밀번호·없는 이메일에 같은 오류 문구.
- L4 로그인 없이 `/manuals`·자료 API 접근 시 로그인 화면 또는 401.
- L5 사용자 A가 사용자 B의 자료·매뉴얼·공유를 조회·수정할 수 없다(DB 통합 테스트).
- L6 비밀번호가 DB에 해시로만 저장된다.
- L7 로그아웃 후 이전 쿠키로 접근이 막힌다.
- L8 구글 로그인 콜백에서 잘못된 `state`를 거부한다(가짜 구글 응답으로 테스트, 실제 구글 연결은 수동 확인).
- L9 로그인 시도 횟수 제한이 동작한다.
- L10 후임자 공유 링크가 로그인 없이 열리고 취소 후 막힌다.
- L11 기존 단위·통합·E2E·접근성 검사를 새 흐름(가입 후 시작)에 맞게 고친 뒤 모두 통과한다.

## 12. 사용자 확인이 필요한 것

1. 후임자 공유 링크는 로그인 없이 보게 할지(제안), 후임자도 로그인해야 할지.
2. 이메일 인증이 없는 동안 구글 계정과 이메일 계정을 자동 연결할지, 로그인한 상태에서만 연결할지(제안: 로그인한 상태에서만).
3. 일정이 밀릴 때 구글 로그인을 뒤로 미루는 것에 동의하는지.

## 13. 구현자에게 남긴 판단

- 구글 OAuth를 직접 구현할지 작은 라이브러리(예: `arctic`, `oauth4webapi`)를 쓸지
- 사용자 문서함의 `expires_at` 처리 방식, 사용자당 자료 상한 값
- 로그인 필요 화면의 리디렉션 방식(서버 컴포넌트 검사 또는 미들웨어)
- 랜딩 페이지 문구·배치 세부, 기존 `Start` 화면 재사용 범위
- scrypt 매개변수 값
