# 랜딩 페이지·로그인 설계

변경일: 2026-10-23 (KST). 상태: 설계 초안, 사용자 승인 대기. 제품 코드·schema·배포는 아직 바꾸지 않았다.

## 1. 결정과 이유

2026-10-23 멘토링 피드백으로 사용자가 다음을 정했다.

- 서비스가 무엇인지 한눈에 보이는 **랜딩 페이지**를 만든다. 화면은 간결하게 한다.
- **로그인을 만든다.** 방식은 **이메일+비밀번호(이메일 인증 필수)와 구글 간편 로그인 둘 다**다.
- **로그인 필수로 바꾼다.** 지금의 "로그인 없이 7일 임시 공간" 방식은 없앤다.
- **매뉴얼 공유는 Colab처럼** 처음에는 비공개이고, 작성자가 "링크가 있는 사용자 볼 수 있음"으로 바꿀 수 있다. 보는 사람도 로그인해야 한다.
- 중간평가(2026-11-06)까지 순서는 **랜딩 → 로그인 → 엑셀 비교**다. 로그인이 늦어지면 구글 로그인을 뒤로 미룬다(사용자 동의).

근거: 멘토 피드백(보안 문제, 로그인 필요, 서비스가 명확히 보이는 화면). 판매·관리 기능(어드민·구독·로고)은 이번 범위가 아니다.

## 2. 목표

- 처음 방문한 사람이 랜딩 페이지에서 서비스가 무엇이고 어떻게 쓰는지 30초 안에 이해한다.
- 이메일로 가입하고, 메일로 받은 링크로 인증한 뒤 로그인·로그아웃할 수 있다.
- 구글 계정으로 가입·로그인할 수 있다.
- 로그인한 사용자는 자기 문서함 하나를 갖고, 자료가 7일 뒤 지워지지 않는다.
- 매뉴얼은 기본 비공개이고, 작성자가 링크 공유를 켜고 끌 수 있다.
- 다른 사용자의 자료는 볼 수도 바꿀 수도 없다. 링크 공유가 켜진 매뉴얼의 게시 버전만 예외로 읽을 수 있다.
- 기존 기능(자료 등록·매뉴얼 작성·검수·게시·질문)은 그대로 동작한다.

## 3. 비목표

- 팀 생성·초대·팀 권한, 특정 사람에게만 공유, 어드민 페이지, 사용량 제한·구독 결제, 회사 로고. 후속(사업화)이다.
- ~~비밀번호 찾기~~ → 2026-10-28 팀 피드백으로 범위에 포함(16절).
- 구글 외 소셜 로그인(카카오·네이버 등).
- JWT. 이유는 6절.
- 기존 익명 임시 공간의 자료를 계정으로 옮기기. 배포 후 7일 안에 만료된다.

## 4. 실패로 보는 경우

- 로그인 없이, 또는 비공개 매뉴얼을 다른 사용자가 볼 수 있다.
- 인증하지 않은 이메일 계정으로 로그인할 수 있다.
- 비밀번호나 인증 링크 토큰을 평문으로 저장하거나 로그에 남긴다.
- 로그인 화면이 복잡해서 심사위원·후임자가 쓰기 어렵다.
- 랜딩 페이지가 기능 설명으로 길게 늘어진다.
- 기존 매뉴얼 흐름·접근성 검사가 깨진다.

## 5. 화면

### 5.1 랜딩 페이지 (`/`, 로그인 없이 볼 수 있음)

간결하게 한 화면 반 정도로 구성한다.

1. **첫 화면:** 한 문장 소개와 버튼 두 개(`시작하기` → 가입, `로그인`). 소개 문장 예: "작업을 마친 업무 파일을 올리면, 바뀐 부분의 이유를 묻고 후임자용 인수인계 매뉴얼로 남깁니다."
2. **사용 순서 3단계:** 파일 올리기 → 바뀐 부분 질문에 답하기 → 후임자에게 공유.
3. **차별점 3개:** 버전 기록, 변경 이유 질문, 검수된 매뉴얼과 근거.
4. **아래쪽:** 개인정보·이용약관 링크(기존 화면).

로그인한 사용자가 `/`에 오면 버튼 자리에 `내 문서함으로`를 보여준다. 아직 만들지 않은 기능(파일 비교)은 "준비 중"으로 표시하고 이미 되는 것처럼 쓰지 않는다.

### 5.2 가입·인증·로그인

- **가입 (`/signup`):** 이름, 이메일, 비밀번호 입력 → "인증 메일을 보냈습니다" 화면. 메일의 링크를 누르면 인증이 끝나고 로그인된다.
- **인증 링크:** 24시간 유효, 한 번만 쓸 수 있다. 만료되면 로그인 화면에서 `인증 메일 다시 보내기`를 누른다(시간당 횟수 제한).
- **로그인 (`/login`):** 이메일·비밀번호와 `구글로 계속하기` 버튼. 인증 전 계정은 "이메일 인증을 먼저 완료하세요"와 재발송 버튼을 보여준다.
- 오류 문구는 "이메일 또는 비밀번호가 올바르지 않습니다"처럼 어느 쪽이 틀렸는지 알려주지 않는다.
- 로그인 후 `/manuals`(내 문서함)로 이동한다. 상단 내비게이션에 이름과 `로그아웃`을 둔다.

### 5.3 매뉴얼 공유 (Colab 방식)

- 매뉴얼마다 공유 설정이 있다. **기본값은 `비공개`**(작성자만 볼 수 있음).
- 작성자가 `링크가 있는 사용자 볼 수 있음`으로 바꾸면 링크를 복사할 수 있다. 이 링크를 연 사람은 **로그인한 뒤** 게시된 버전만 읽기 전용으로 본다. 수정·삭제·질문 기록 조회는 할 수 없다.
- 다시 `비공개`로 바꾸면 그 링크로 더는 볼 수 없다.
- 로그인하지 않은 사람이 링크를 열면 로그인 화면으로 보내고, 로그인 후 원래 링크로 돌아온다.
- 게시되지 않았거나 재검토가 필요한 매뉴얼은 링크 공유를 켤 수 없다(기존 공유 조건 유지).
- 지금의 공유 토큰·만료 방식은 이 설정으로 바꾼다. 링크를 바꿔 이전 링크를 무효로 하는 `링크 새로 만들기`는 구현자 판단으로 넣을 수 있다.

## 6. 로그인 방식

- **세션:** 지금 쓰는 방식(무작위 토큰을 HttpOnly 쿠키로 주고, DB에는 토큰 해시만 저장)을 그대로 쓰고, 세션에 사용자를 연결한다.
- **JWT를 쓰지 않는 이유:** JWT는 서버가 기록 없이 토큰만 검사하므로, 로그아웃·계정 삭제·탈취 시 즉시 끊기가 어렵다. 지금 구조는 DB 세션 행을 지우면 바로 끊긴다. 서버 한 대 규모라 JWT의 장점(서버 여러 대에서 DB 조회 없이 확인)도 필요 없다.
- **비밀번호:** Node 내장 `scrypt`로 사용자별 salt와 함께 해시한다. 8자 이상 128자 이하. 비교는 시간 일정 비교를 쓴다.
- **이메일 인증:** 무작위 토큰을 메일 링크로 보내고 DB에는 해시만 저장한다. 인증 전에는 로그인 세션을 만들지 않는다.
- **구글 로그인:** OAuth 2.0 인가 코드 방식 + PKCE + `state` 검사. 구글이 확인한 이메일(`email_verified=true`)만 받으며, 구글 계정은 가입 즉시 인증된 것으로 본다. 사용자 식별은 구글 계정 고유 ID(`sub`)로 한다.
- **계정 연결:** 두 방식 모두 이메일이 인증되므로, 구글 이메일이 기존 **인증된** 이메일 계정과 같으면 같은 계정에 자동 연결한다. 인증되지 않은 이메일 계정과 같으면 구글 쪽으로 계정을 넘기고 기존 미인증 비밀번호는 지운다(남의 이메일로 먼저 가입해 둔 경우를 막기 위해).
- **세션 기간:** 30일. 로그아웃하면 해당 세션 행을 지운다.
- **요청 보호:** 기존처럼 변경 요청은 `Origin` 검사, 쿠키는 `HttpOnly; SameSite=Lax; Secure(https)`. 로그인·가입·인증 메일 재발송은 IP 기준 시도 횟수 제한(기존 `rate_counters` 사용)을 둔다.

## 7. 데이터 (제안)

- `users`: id, email(소문자 저장, 유일), name(1~40자), password_hash(구글 전용이면 비어 있음), google_sub(유일, 비어 있을 수 있음), email_verified_at, created_at.
- `email_verifications`: id, user_id, token_hash(유일), expires_at, used_at.
- `workspaces`: `user_id`를 추가한다. 사용자당 문서함 하나. 사용자 문서함은 만료되지 않는다(`expires_at` 처리는 구현자 판단).
- `sessions`: `user_id`를 추가한다. 익명 owner/reader 세션 구분은 없앤다.
- `manuals`: `link_sharing`(`private` 기본, `link`)과 링크용 무작위 ID를 추가한다. 기존 `shares` 테이블은 이 방식으로 대체한다.
- 기존 익명 workspace 행은 그대로 두고 기존 7일 정리로 사라지게 한다.
- 파일 버전 설계의 "올린 사람·팀 직접 입력"은 **이름을 계정 이름으로 자동 기록**하고, 팀은 계정 설정에서 직접 입력하는 것으로 바꾼다. 팀 계정은 후속이다.

## 8. API (제안)

| 메서드·경로 | 동작 |
|---|---|
| POST `/api/auth/signup` | 이메일·이름·비밀번호로 가입, 인증 메일 발송 |
| GET `/api/auth/verify?token=` | 인증 완료, 문서함 생성, 로그인 쿠키 발급 후 `/manuals`로 이동 |
| POST `/api/auth/verify/resend` | 인증 메일 다시 보내기 |
| POST `/api/auth/login` | 이메일·비밀번호 로그인(인증된 계정만) |
| POST `/api/auth/logout` | 현재 세션 삭제 |
| GET `/api/auth/google` | 구글 로그인 시작(state·PKCE 저장 후 이동) |
| GET `/api/auth/google/callback` | 구글 응답 확인, 가입 또는 로그인 후 이동 |
| GET `/api/me` / DELETE `/api/me` | 로그인 사용자 정보 / 계정과 문서함 전체 삭제 |
| PUT `/api/manuals/:id/sharing` | `private` 또는 `link`로 변경 |
| GET `/api/shared/:linkId` | 링크 공유가 켜진 매뉴얼의 게시 버전 읽기(로그인 필요) |

기존 `POST /api/workspaces`(익명 공간 만들기)와 공유 토큰 교환 API는 없앤다. 합성 예제는 문서함 안의 `예제 불러오기` 버튼으로 옮긴다(작성자 판단).

## 9. 메일 발송·보안·운영

- **메일 발송은 Gmail SMTP를 쓴다**(사용자 결정). 팀 Gmail 계정에 2단계 인증을 켜고 앱 비밀번호를 만들어 서버 `.env`(`SMTP_USER`, `SMTP_APP_PASSWORD`)에만 넣는다. Git·문서·로그에 쓰지 않는다. DNS 설정은 필요 없다.
- Gmail은 하루 발송 한도(일반 계정 약 500통)가 있고 받는 쪽에서 스팸으로 분류될 수 있다. 데모 규모에는 충분하며, 화면에 "메일이 안 보이면 스팸함을 확인하세요"를 안내한다. 사용자가 늘면 Resend·AWS SES로 바꿀 수 있도록 발송 부분을 함수 하나로 분리한다.
- 테스트에서는 실제 메일을 보내지 않고 가짜 발송기로 링크를 확인한다.
- 구글 로그인에는 Google Cloud에서 OAuth 클라이언트를 만들어야 한다. 사용자가 직접 만들고, 값은 서버 `.env`(`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`)에만 넣는다. 리디렉션 주소: `https://ghostmanual.pigs0516.com/api/auth/google/callback`, 로컬 `http://localhost:3200/api/auth/google/callback`.
- 비밀번호를 잊으면 이메일 재설정 링크로 다시 정한다(16절).
- 개인정보 처리방침에 계정 정보(이메일·이름)와 보관·삭제 방법을 추가하고, 7일 자동 삭제 문구를 바꾼다.
- 서버 저장 용량: 7일 만료가 없어지면 자료가 쌓인다. 사용자당 자료 수·크기 상한을 둔다(값은 구현자 판단).

## 10. 테스트와 인수 조건

- L1 랜딩 페이지가 로그인 없이 열리고, 데스크톱·모바일에서 가로 넘침이 없다.
- L2 이메일 가입 → 인증 메일 링크 → 로그인 상태로 내 문서함 진입 → 로그아웃 → 다시 로그인.
- L3 인증 전 계정은 로그인할 수 없고, 만료·사용된 인증 링크는 거부된다.
- L4 틀린 비밀번호·없는 이메일에 같은 오류 문구.
- L5 로그인 없이 `/manuals`·자료 API·공유 링크 접근 시 로그인 화면 또는 401.
- L6 사용자 A가 사용자 B의 자료·매뉴얼을 조회·수정할 수 없다(DB 통합 테스트).
- L7 비공개 매뉴얼은 링크를 알아도 다른 사용자가 볼 수 없고, `링크 공유`로 바꾸면 로그인한 다른 사용자가 게시 버전만 읽는다. 다시 비공개로 바꾸면 막힌다.
- L8 비밀번호·인증 토큰·세션 토큰이 DB에 해시로만 저장된다.
- L9 로그아웃 후 이전 쿠키로 접근이 막힌다.
- L10 구글 콜백에서 잘못된 `state`를 거부하고, 인증된 같은 이메일 계정에 연결된다(가짜 구글 응답으로 테스트, 실제 구글은 수동 확인).
- L11 로그인·재발송 시도 횟수 제한이 동작한다.
- L12 기존 단위·통합·E2E·접근성 검사를 새 흐름(가입 후 시작)에 맞게 고친 뒤 모두 통과한다.

## 16. 2026-10-28 팀 피드백 반영

박기성 검토 피드백을 반영했다.

- **공유 링크 → 가입 → 원래 문서:** 로그인 화면의 가입 링크, 가입 화면의 Google 버튼, 인증 메일 링크가 모두 목적지(`next`, 같은 사이트 경로만)를 넘긴다. 인증 후 원래 공유 문서로 이동한다. E2E로 확인.
- **비밀번호 찾기:** 로그인 화면 "비밀번호를 잊으셨나요?" → 이메일 입력 → 재설정 링크(1시간·1회, 토큰은 해시만 저장, 링크의 `#` 뒤에 실어 서버 기록·Referer에 남지 않음) → 새 비밀번호 두 번 입력 → 그 계정의 모든 세션 종료 → 로그인. 없는 이메일도 같은 화면이며 메일은 가지 않는다. 링크가 메일함 소유를 증명하므로 미인증 계정은 인증 완료로, 구글 전용 계정은 비밀번호가 추가된다. IP당 시간당 5회 제한.
- **이미 가입된 이메일로 가입:** 화면은 같고, 그 주소로 "이미 가입된 계정" 안내 메일을 보낸다(가입 여부를 남에게 드러내지 않으면서 주인에게는 알림).
- **DB 변경:** `003_password_resets.sql`(테이블 1개 추가). 운영 적용은 박기성이 배포 때 수행한다.
- **결정 대기:** 운영 DB 백업(현재 없음, 제안: 매일 덤프·7일 보관), 오래 쓰지 않은 계정 정리 여부. 박기성·박효민이 정한 뒤 이 문서와 개인정보 안내에 반영한다.
- **약관 동의(A안, 박기성 피드백 후 사용자 결정):** "Google 계정으로 계속하기"는 계정이 없으면 만들고 로그인하는 동작을 유지한다. 대신 이메일 가입은 약관·개인정보 동의 체크가 필수이고, 구글로 처음 만들어진 계정과 기존 미동의 계정은 공통 약관 동의 화면(`/welcome`)을 거친다. 동의 전에는 서버가 문서·자료 API를 `terms_required`(403)로 막고 동의·내 정보·로그아웃·계정 삭제만 허용한다. 동의하지 않고 나가면 가입 시각과 관계없이 로그아웃만 하며 계정과 저장된 자료는 유지한다. 계정 삭제는 별도의 명시적인 삭제 흐름에서만 수행한다. 미인증 이메일 계정을 구글이 넘겨받으면 동의를 다시 받는다.
