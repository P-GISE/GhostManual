# 문서함·파일 등록·읽기 격리 기준선

## 범위와 실행

사용자는 PR120 검증 후 병합과 지연 측정을 지시했고 운영 반영·migration014 적용은 보류했다. 별도 GitHub Actions 전용 PostgreSQL service와 Chromium 한 명으로 측정한다. 로컬 프로젝트/S1에서 빌드·벤치를 실행하지 않고 실제 계정·업무 자료·외부 AI·메일을 사용하지 않는다.

전용 workflow는 `chore/document-latency-baseline` push에서만 실행한다. localhost3200·전용 `ghostmanual_latency_test`·GitHub Actions·AI=false 가드를 통과해야 setup/측정을 시작한다. 빈 DB에001~013만 구성하며014·운영DB·backfill은 실행하지 않는다. 앱·API·큐 구현·의존성·폴링 간격·권한 정책을 수정하지 않는다.

## 표본과 경계

합성 회원1명과 팀3개, DOCX/HWPX/PPTX 형식별 작은 패키지31개를 사용한다. 각 형식의 첫1회는 워밍업으로 분리하고 나머지30회에서 nearest-rank p50/p95를 계산한다. 원본 추출 표식을 확인하고 게시·다운로드 차단과202 접수를 실제 추출 완료와 구분한다. 등록/읽기 중 팀별 자료 수는1→31로 증가하므로 고정 자료 수 부하 비교라고 해석하지 않는다.

- 등록 화면: 새 문서 주소 진입→권한 확인 뒤 제목 입력 가능.
- 등록 접수: 등록 클릭→브라우저 해시/유사 자료 조회→POST202 JSON 수신.
- 추출: 기존 claim 함수, native extract, complete 함수를 변경 없이 호출해 각각의 경과 시간을 분리한다.
- 큐 관측 나이: pending 화면/다운로드 차단 확인 후 제어된 claim까지의 나이. 실제 운영 worker의 idle/스케줄 지연을 대체하지 않는다.
- 화면 감지: 저장 완료 뒤 현재 UI의 다운로드 링크 표시까지. 기존2초 폴링을 유지한다.
- 읽기: ready 문서 reload→상세/현재 추출 내용을 펼쳐 표식 표시까지.
- 문서함: 팀3개·파일93개 고정 상태에서31회 진입, 첫1회 제외30회. 팀별 제한10개씩 총30카드로 검증한다.

시간은 harness 단조시계 기준 자동화 milestone이며 실제 이용자 체감·네트워크·페인트/LCP/INP 전부를 뜻하지 않는다. 캐시를 강제로 끄지 않으며 워밍업 이후 비교용 기준선이다. runner CPU/메모리와 Node버전·commit/run·입력 바이트·표본 수를 함께 남긴다.

## 수집·보존과 한계

산출물 `user-flow-latency.json`에는 합성 case 구분·시간·HTTP status·ID/검색어를 제거한 API 경로 분류·decoded body 바이트와 원시 표본만 둔다. 쿠키/토큰/메일 주소/원문/DB 연결 문자열은 기록하지 않는다. API 응답은 phase 관측 창에서 응답을 받은 요청이며 wire 바이트나 모든 지연/취소 요청의 전체 개수로 해석하지 않는다.

DB 개별 SQL/잠금 대기·Next/DB 프로세스 RSS/CPU·생산 cgroup 상한·OCR·다중 동시 사용자·5MiB 경계는 이번 첫 기준선에서 측정하지 않는다. resourceUsage는 harness와 inline native 추출 범위다. 이 한계를 숨기지 않고 후속 계측으로 분리한다. 전체 권한 회귀는 기존 CI와 함께 확인한다.

404·문서함503 입력 차단·처리 전 다운로드409와 payload별 ready/원문 표식이 측정 경계의 오류 대조다. 이번 데이터만으로 서비스 개선율이나 운영 용량을 보증하지 않는다. 측정 결과·실패·최종 커밋/CI는 후속 PR 본문에 기록하고, 병목 기여가 확인된 가장 작은 변경만 다음 작업으로 선택한다.

Ruling: 기존 계획의 넓은 행렬 대신 한 사용자·작은 native3형식부터 시작한다. 공유 서버/OCR 부하와014를 피하면서 실제 UI·HTTP·처리 대기를 구분하기 위한 첫 단계이며, 미측정 구간을 전체 성능 결과로 확대하면 잘못된 최적화를 선택할 수 있다.
