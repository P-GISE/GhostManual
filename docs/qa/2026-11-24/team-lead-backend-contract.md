# 대표 관리자·부관리자 권한과 명시적 이양 API 계약

## 현재 합의·단계

사용자는 #98의 **권한표만** 채택했다. 개인 문서함·기존 개인/팀 자료·매뉴얼·답변·양식·공유 링크·Reader는 유지한다. 화면/상단 메뉴/공유 구역 제거·자동 업무 이동·자동 승계는 이번 범위가 아니다. 기존 DB 역할은 admin/member 두 가지이며 부관리자는 별도 enum이 아니라 **준비된 팀에서 admin이면서 lead=false인 사람**이다.

현재 운영 #106/DB013은 이전 단계다. 이번 PR107의 새 권한표 코드는 먼저 DB013 호환 상태로 검증·반영해야 하며, #106만으로014 후 새 권한표가 충족되지는 않는다.014 운영 적용·대표 지정·새 앱 운영 배포는 이번 작업에서 하지 않는다.

준비 신호는 DB 소유자가 제약과 같은 트랜잭션에 기록하는 `schema_migrations.name='014_team_lead_enforce.sql'`이다. 매 TX에서 읽고 환경 변수·캐시·사용자 입력으로 켜지 않는다. 현재 운영 앱 역할은 이 표 SELECT만 가능하고 INSERT/UPDATE/DELETE는 불가능한 것을 이전013 검증에서 확인했다.

## 014 적용 전·후 권한

013에만 있는 팀은 기존 admin 권한을 유지하고 이양 POST는503을 반환한다. 일반 팀원을 admin으로 올리기, 다른 admin 내보내기, 팀 삭제 등 기존 동작을 새 권한표로 미리 제한하지 않는다. 대표·부관리자 표시도 미준비 상태에 붙이지 않는다.

실제014가 적용된 팀에서는 다음 표를 따른다.

| 동작 | 대표 관리자 | 부관리자(admin·대표 아님) | 일반 팀원 |
|---|---|---|---|
| 초대·초대 취소·팀 이름 변경 | 허용 | 허용 | 거절 |
| 승격·강등(자기 강등 포함) | 허용, 대표 자기 강등은 이양 전409 | 거절 | 거절 |
| 일반 팀원 내보내기 | 허용 | 허용 | 거절 |
| 다른 부관리자 내보내기 | 허용 | 거절 | 거절 |
| 대표 내보내기 | 대표 본인도 이양 전409 | 거절 | 거절 |
| 본인 팀 나가기 | 이양 전409 | 허용 | 허용 |
| 팀 삭제 | 허용 | 거절 | 거절 |
| 대표 이양 | 다른 현재 팀원에게 명시적으로 허용 | 거절 | 거절 |

대표인 팀이 하나라도 있으면 계정 삭제는 개인 자료 제거 전에409로 거절한다. 이양 후 이전 대표는 admin으로 남고 부관리자가 되며, 본인 나가기/계정 삭제는 기존 보존 정책 안에서 가능하다. 다른 admin을 내려서 삭제 제한을 우회하는 권한은 부관리자에게 주지 않는다.

자료·매뉴얼·답변·양식·공유의 기존 작성자/admin 경계는 이 표로 변경하지 않는다. 이 표는 팀 관리 동작의 범위이며 새 전체 조회/진행 현황 API를 구현한 것이 아니다.

## 응답·POST 계약

`GET /api/workspaces/:id/members`의 기존 추가 필드를 유지한다.

- `leadReady`:014 marker와 non-NULL 팀 pointer가 있을 때 true.
- `leadUserId`: 준비된 팀의 canonical 대표 UUID, 준비 전 NULL.
- `members[].lead`: 준비된 pointer와 팀원 UUID가 같은지 계산.
- `members[].role`은 admin/member 그대로다. member에게 이메일·대기 초대를 노출하지 않는 기존 경계를 유지한다.

`POST /api/workspaces/:id/lead`는 정확히 `{ "userId": "<uuid>" }`를 받는다. 세션·약관·same-origin·JSON/UUID 검사를 유지하고 workspace를 정렬 잠근 뒤 현재 소속·역할·대표 pointer를 다시 읽는다. actor는 현재 대표, 대상은 **같은 팀의 다른 현재 admin 또는 member**여야 한다. 자기 UUID의 대문자 표기도 DB UUID 비교로 거절한다.

대상이 member이면 **이번 명시적 이양 요청의 같은 TX 안에서만** admin으로 올린 뒤 pointer를 바꾼다. 대상이 admin이면 역할을 다시 쓰지 않는다. 두 사람 모두 최종 admin이며 이전 대표는 lead=false다. pointer 저장 실패 시 승격도 전체 rollback한다. 이는 backfill·가입·탈퇴 때의 자동 승격/자동 승계가 아니다.

성공 응답은 `{ "id": "<workspace uuid>", "leadUserId": "<canonical target uuid>" }`이고 쿠키를 교체하지 않는다. 추가 GET 필드나 새 역할 enum은 만들지 않는다.

## 오류·세션

- 401: 유효 로그인/세션 없음.
- 403: origin 또는 현재 역할/대표 조건 불충족(`forbidden`, `lead_required`).
- 404: 비회원·Reader·없는 팀/팀원.
- 422: 잘못된/추가 입력, 자기 자신, 현재 같은 팀 팀원이 아닌 이양 대상.
- 503 `team_lead_not_ready`:014 미적용 또는 준비 신호 뒤에도 pointer가 없는 비정상 상태.
- 409 `lead_transfer_required`: 현재 대표의 자기 강등·자기 나가기·계정 삭제에 먼저 이양이 필요함.

팀 나가기의 자기 판별은 user UUID를 canonical 비교하고, 선택한 팀의 대문자 UUID도 같은 팀으로 판단한다. 일반 팀원·부관리자의 자기 나가기는 새 개인 세션을 발급하고 이전 팀 토큰을 폐기한다. 대표 자기 나가기는 이양 전 거절한다. 거절된 동작은 쿠키·기존 세션·자료를 바꾸지 않는다.

계정 삭제는 **현재 소속된 모든 팀**과 개인/현재 workspace를 정렬 잠근 뒤 대표 여부를 검사한다. 이양 대상이 일반 팀원에서 admin/대표가 될 수 있으므로 admin 팀만 잠그는 이전 가정을 사용하지 않는다. 후속 마지막 admin 검사는 유지한다.

## 경합·검증 경계

같은 팀 workspace 잠금이 역할 변경·내보내기·이양·계정 삭제를 직렬화한다. 예전 대표의 요청이 대기하는 동안 이양되면 권한을 다시 읽어403으로 거절한다.

이양과 대상 승격/강등은 역할 변경이 먼저 완료되면 둘 다 성공할 수 있다. 그 뒤 명시적 이양이 현재 member를 다시 admin으로 올리는 것은 정상 순서다. 이양이 먼저 완료되면 이전 대표의 뒤늦은 역할 변경은403이다. 대상 자기 탈퇴/계정 삭제와 이양은 한 동작만 성공하고 다른 동작은409 또는422로 거절한다. 일반 API 경합에서 임의 DB 오류/503을 성공으로 인정하지 않는다.

새 RED31fb0ab/CI45326031071에서 기존227건과 새3건은 통과하고 권한·명시적 member 이양·13/14 UUID 자기 탈퇴·삭제 첫 잠금·대기 중 이전 대표 검증12건이 실패하는 것을 확인한 뒤 수정했다. 실제014 정책 검사는 기본 CI DB에서,013 구버전 계약/marker 프로토콜은 별도 고유 테스트 DB에서 검사한다. 구현69e5af8/CI45326607263에서013/014 DB242건이 통과했다. 최종 head의 전체 CI·코드 검토 결과는 PR107을 따른다.
